# 추후 수정 및 검증 필요 사항

> 작성일: 2026-08-04  
> 대상 버전: 0.1.0  
> 검토 방식: 문서·소스·기존 테스트를 읽고 비교한 정적 검토

이 문서는 `orca-vision-helper`의 현재 구현에서 추후 수정하거나 추가로 검증해야 할
사항을 기록한다. 이번 검토에서는 프로그램 설치, 설정 변경, 네트워크 호출, 테스트
실행 및 기존 코드 수정은 수행하지 않았다. 따라서 아래 항목 중 실제 실행 환경과 관련된
내용은 수정 시 재현 테스트와 제공자별 종단 간 검증이 필요하다.

## 2026-08-04 후속 작업 상태

- 완료: 1~7의 코드 수정과 회귀 테스트
- 부분 완료: 8의 키 없는 custom 로컬 HTTP 서버 기반 CLI 종단 간 테스트
- 완료: 9의 다중 OS/Python CI, MIT `LICENSE`, `CHANGELOG.md`
- 완료: 10의 최초 설치 시 버전별 클라우드 전송 동의, 직접 키 인자 경고,
  custom HTTP/HTTPS 보안 문서화
- 남음: 실제 자격 증명이 필요한 제공자별 opt-in 통합 검증

아래 내용은 최초 검토 기록으로 보존한다. 완료 표시는 구현과 자동 테스트 기준이며,
외부 제공자의 실제 서비스 호환성을 의미하지 않는다.

## 현재 상태 요약

현재 코드는 CLI, 제공자 레지스트리, 키 해석, 이미지 전처리, 세 종류의 API 형식
(OpenAI 호환·Anthropic·Ollama), 구조화 보고서 파싱 및 오류 매핑을 구현한 v0.1/M1
단계다. 단위 테스트는 요청 형식과 주요 실패 경로를 비교적 상세하게 다루지만 대부분
HTTP와 키체인을 mock 처리한다. OpenCode 이외 제공자의 실제 종단 간 호환성은 아직
충분히 입증되지 않았다.

## 우선순위 높음

### 1. 키 없는 custom 제공자가 CLI에서 차단됨

- `providers.py`는 custom 제공자의 키를 선택 사항으로 선언한다.
- `OpenAICompatibleBackend`도 키가 없는 custom 요청을 허용한다.
- 그러나 `cli._cmd_analyze()`는 Ollama가 아닌 모든 제공자에 키가 없으면
  `AUTH_FAILED`를 반환한다.
- `check`도 키 없는 custom 제공자를 실패로 판정한다.
- README의 "keyless gateways supported" 설명 및 백엔드 단위 테스트와 실제 CLI
  동작이 일치하지 않는다.

수정 시 확인할 사항:

- 인증 필요 여부를 `provider.is_local`이 아니라 `ProviderSpec.key_required` 기준으로
  판단한다.
- `analyze`, `check`, `provider list`의 `has_key` 의미를 일관되게 정한다.
- 키 없는 custom 제공자를 CLI 전체 경로로 호출하는 회귀 테스트를 추가한다.

### 2. Anthropic `check`의 점검 URL과 성공 판정

- Anthropic 기본 URL은 이미 `/v1/messages`까지 포함하지만 `check`는 모든 클라우드
  제공자 URL 뒤에 `/models`를 붙인다.
- 결과적으로 Anthropic은 `/v1/messages/models`라는 잘못된 URL을 점검할 수 있다.
- 일반 클라우드 점검에서 HTTP 401과 403도 성공으로 인정하므로 잘못된 URL이나 인증
  실패를 정상 연결로 오인할 가능성이 있다.

수정 시 확인할 사항:

- 제공자 인터페이스별 전용 probe URL과 기대 상태 코드를 정의한다.
- 연결 가능, 인증 유효, 모델 사용 가능 여부를 별도 필드로 구분한다.
- `check`가 단순 연결성 검사인지 실제 사용 가능성 검사인지 문서에 명시한다.

### 3. 제공자 타입 변경 시 설정이 일관되지 않을 수 있음

- `provider update --type`은 타입만 변경하고 base URL, 기본 모델, 키 요구 조건을 새
  타입에 맞게 갱신하지 않는다.
- 예를 들어 OpenAI 제공자를 Anthropic으로 변경해도 기존 OpenAI URL과 모델이 남을
  수 있다.
- Anthropic 백엔드는 저장된 `provider.base_url`을 사용하지 않고 고정 API URL을
  사용하므로 설정에 표시되는 값과 실제 요청 대상이 달라질 수 있다.

수정 시 확인할 사항:

- 타입 변경을 금지하거나, 타입 변경 시 관련 기본값을 원자적으로 재설정한다.
- 사용자가 지정한 Anthropic base URL을 지원할지 명시적으로 결정한다.
- 타입 변경 후 `provider list`, `check`, `analyze`가 같은 설정을 참조하는지 검증한다.

## 우선순위 중간

### 4. 일부 오류가 구조화된 JSON 대신 traceback으로 끝날 수 있음

현재 `VisionError`로 변환되지 않을 가능성이 있는 경로:

- 경로가 디렉터리이거나 손상된/지원하지 않는 이미지일 때의 Pillow 예외
- HTTP 2xx 응답 본문이 JSON이 아닐 때의 `resp.json()` 예외
- 응답 JSON의 자료형이나 필드 구조가 예상과 다를 때의 예외
- 문법상 올바르지만 Pydantic 스키마와 맞지 않는 설정 파일

수정 시 확인할 사항:

- 이미지 열기·전처리 오류를 `BAD_REQUEST`로 매핑한다.
- 제공자 응답 디코딩과 구조 검증 오류를 `RESPONSE_INVALID`로 매핑한다.
- 설정 검증 실패에 대한 복구 또는 명확한 사용자 안내 정책을 정한다.
- CLI 실패가 일관된 오류 스키마와 종료 코드 1을 반환하는지 테스트한다.

### 5. Ollama 자유 형식 프롬프트도 JSON 출력을 강제함

- README는 `--prompt`가 스키마 없는 자유 형식 요청이라고 설명한다.
- `BaseBackend.analyze(..., schema=False)`는 보정 재요청을 생략한다.
- 그러나 Ollama 요청 본문은 항상 `"format": "json"`을 포함한다.
- 따라서 Ollama의 자유 형식 동작은 문서 및 다른 제공자와 다르다.

수정 시 확인할 사항:

- `_complete`에 schema/response-format 의도를 전달하거나 요청별 형식을 별도로 구성한다.
- 자유 형식 응답과 구조화 응답의 CLI 출력 계약을 제공자 간 통일한다.

### 6. 설정 파일 손상 처리 정책이 일관되지 않음

- JSON 문법이 깨진 설정은 경고 없이 빈 설정으로 대체된다.
- JSON 문법은 맞지만 필드가 잘못된 경우에는 Pydantic 검증 오류가 전파될 수 있다.
- 자동으로 빈 설정을 반환하면 기존 설정이 사라진 것처럼 보여 사용자가 재설정을
  시도할 위험도 있다.

수정 시 확인할 사항:

- 손상된 설정을 백업하고 명확한 오류를 반환할지 결정한다.
- JSON 파싱 실패와 스키마 검증 실패를 동일한 정책으로 처리한다.
- 잘못된 설정을 읽은 직후 새 빈 설정으로 덮어쓰지 않도록 보호한다.

### 7. 이미지 로딩 단계의 자원 제한 부족

- 긴 변 1568px 제한은 API 전송 비용을 줄이지만 Pillow가 원본 전체를 메모리에 로드한
  다음 적용된다.
- 매우 큰 이미지나 압축 폭탄에 대한 메모리 보호 수단은 아니다.
- 파일 크기, 총 픽셀 수, 허용 형식에 대한 명시적 사전 제한이 없다.

수정 시 확인할 사항:

- 파일 크기와 이미지 픽셀 수 상한을 정의한다.
- Pillow의 decompression-bomb 경고/오류를 사용자 친화적인 오류로 변환한다.
- 일반적인 고해상도 스크린샷을 불필요하게 거부하지 않는 한계를 정한다.

## 배포 및 운영 완성도

### 8. 실제 제공자 통합 검증 확대

- 기존 API 테스트는 대부분 `httpx.post`를 mock 처리한다.
- OpenCode 조사 기록 외에 Anthropic, OpenRouter, OpenAI, Ollama, custom의 실제 이미지
  분석 성공을 재현하는 자동화 증거가 없다.
- 모델명, 요청 형식과 응답 형식은 제공자 정책 변경의 영향을 받을 수 있다.

권장 작업:

- 기본 테스트와 분리된 opt-in 통합 테스트를 마련한다.
- 키 없는 custom 서버는 로컬 mock HTTP 서버로 CLI 전체 경로를 검증한다.
- 제공자별 최소 1개 비전 모델로 요청, 파싱, 오류 출력을 확인한다.
- 실제 키와 이미지가 CI 로그나 테스트 산출물에 노출되지 않게 한다.

### 9. CI와 배포 메타데이터

- 저장소에 CI 설정이 없다.
- `pyproject.toml`은 MIT 라이선스를 선언하지만 별도의 `LICENSE` 파일이 없다.
- 변경 기록과 지원 환경별 자동 검증 자료가 없다.

권장 작업:

- Python 3.11 이상과 주요 운영체제에서 lint 및 단위 테스트를 실행하는 CI를 추가한다.
- 실제 MIT 라이선스 전문 파일을 추가한다.
- 릴리스 전 체크리스트 또는 변경 기록을 유지한다.

### 10. 개인정보 및 인증키 취급 보강

- 클라우드 제공자 사용 시 이미지가 외부로 전송된다는 내용은 문서에만 고지된다.
- 설계 문서도 외부 전송 동의 UI를 추후 과제로 남기고 있다.
- `--key -`는 안전한 숨김 입력을 제공하지만 CLI는 키 문자열 직접 전달도 허용하므로
  사용자가 이를 쓰면 셸 기록이나 프로세스 목록에 남을 수 있다.

권장 작업:

- 최초 클라우드 분석 전에 명시적 동의 또는 확실한 경고를 제공한다.
- 실제 키를 명령행 인자로 전달하는 사용법은 비권장 또는 금지하는 방안을 검토한다.
- local/custom URL의 보안 요구 사항과 HTTP 허용 범위를 문서화한다.

## 테스트 보강 후보

- custom keyless 제공자의 `provider add -> check -> analyze` 전체 경로
- 존재하는 디렉터리, 손상 이미지, 비이미지 파일 입력
- 제공자의 비 JSON 2xx 응답과 예상하지 못한 JSON 자료형
- 문법상 정상이나 스키마가 잘못된 config 파일
- Anthropic `check` URL과 상태 판정
- `provider update --type` 후 기본 URL·모델·인증 규칙
- Ollama 자유 형식 프롬프트의 요청 본문과 출력
- 키체인 저장 후 설정 저장 실패, 제공자 삭제와 설정 갱신 간 부분 실패
- 동시 실행 시 제공자 추가·수정·삭제 및 마지막 사용 제공자 갱신

## 권장 처리 순서

1. custom keyless 차단과 Anthropic `check` 문제를 수정한다.
2. 제공자 타입 변경 규칙과 base URL의 의미를 확정한다.
3. 이미지·설정·응답 예외를 구조화된 오류로 통합한다.
4. 자유 형식 요청의 제공자별 동작을 통일한다.
5. 실제 제공자 통합 테스트와 CI를 추가한다.
6. 이미지 자원 제한, 외부 전송 동의, 라이선스 등 운영 항목을 보강한다.
